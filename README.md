# PulsarWeb

Сайт студии разработки цифровых решений. Технические этапы **Stage 1–9** реализованы и проверены: bootstrap, foundation, database, lead module, integrations, marketing UI, refinement, tests и verification. Материалы полного кейса Pulsar Cloud владелец добавит позднее; юридические документы остаются черновиками до заполнения фактических данных. Завершение технических этапов не заменяет подготовку фактического контента и настроек для публичного запуска.

## Requirements

- Windows 11 / PowerShell или другая поддерживаемая Node.js платформа.
- Node.js 24 LTS (проверено на 24.15.0).
- pnpm 11.19.0 — версия закреплена в `package.json`.
- Доступ к интернету для установки пакетов и первоначальной загрузки шрифтов через `next/font/google`.

Стек: Next.js 16 App Router, React 19, TypeScript strict, Tailwind CSS 4, shadcn/ui с Base UI, Lucide, Sonner, Zod 4, Prisma 7 и SQLite / better-sqlite3. Единственный lockfile — `pnpm-lock.yaml`.

## Installation

Из корня проекта:

```powershell
pnpm install --frozen-lockfile
```

Разрешённые native build scripts перечислены в `pnpm-workspace.yaml`. Команды dev, build, typecheck и test сами генерируют Prisma Client, поэтому файлы из `src/generated/prisma` не нужно хранить в Git.

## Environment

Для локального старта достаточно значений по умолчанию. Если нужны другие настройки:

```powershell
Copy-Item .env.example .env
```

Выполняйте копирование только если `.env` ещё не создан. `SITE_URL` должен соответствовать адресу приложения; по умолчанию это `http://localhost:3000`. Настройки Telegram и Resend необязательны. Секреты, runtime-база и generated-файлы исключены из Git.

`SITE_URL` принимает только HTTP(S) origin без реквизитов доступа, подкаталога, query и fragment. Конечный `/` нормализуется. Для production указывайте один и тот же origin при build и запуске: статические SEO-данные создаются на этапе сборки.

## Development

```powershell
pnpm db:deploy
pnpm dev
```

Откройте [localhost:3000](http://localhost:3000). Остановка — `Ctrl+C`. Для другого порта используйте `pnpm dev --port 3100` и соответствующий `SITE_URL` в `.env`.


Если CLI сообщает об отсутствующем `@modelcontextprotocol/sdk`, используйте изолированный pnpm-запуск:

## Foundation

- Общие `Container`, `Section`, `PageHeader`, `SectionHeader`, header и footer задают ширину контента и вертикальный ритм. Inter включает кириллицу, цвета и компоненты сохраняют preset.
- Lucide используется для интерфейсных иконок. Навигация показывает текущую страницу или раздел, мобильный Sheet поддерживает клавиатуру, закрытие по Escape и восстановление фокуса.
- Есть skip link, видимые focus-состояния, достаточные области нажатия и поддержка `prefers-reduced-motion`.
- Общий SEO helper задаёт canonical, OpenGraph и Twitter metadata. Есть sitemap, robots, SVG favicon, серверная OpenGraph-обложка и WebSite JSON-LD без выдуманных реквизитов.
- Юридические черновики исключены из sitemap и имеют `noindex`. Они остаются доступны роботу, чтобы тот мог прочитать эту директиву. Robots не является механизмом защиты данных.
- Собственные страницы 404, локальных ошибок и ошибок root layout. Для восстановления используется `retry()` из установленной версии Next.js; текст внутренних исключений посетителю не показывается.
- Реквизиты в `src/config/site.ts` остаются `null` до получения фактических данных. Аналитика и необязательные cookies не подключены.

## Marketing UI

- Главная: позиционирование, шесть направлений, проект, процесс работы, технологии и интеграции, запуск и сопровождение, работа с данными, знакомство со студией и переход к заявке.
- `/services`: четыре основных продукта — лендинги, корпоративные сайты, интернет-магазины и Telegram. Сопровождение отделено от разработки; «Другой проект» принимает нестандартные задачи. CTA передают направление в `/start`.
- `/projects` и `/projects/pulsar-cloud`: общая графическая обложка и структура кейса. Это не скриншот продукта. Функции, стек, инфраструктура, интеграции, результаты и реальные экраны будут опубликованы после получения материалов от владельца; выдуманные показатели не используются.
- `/about`: подход, принципы, этапы, совместная работа и внимание к данным.
- `/start`: единый wizard заявки; выбор проекта, описание, бюджет/срок, контакты и проверка перед отправкой. `/contacts` содержит прямую связь и ссылку на wizard; старые ссылки с выбранной услугой перенаправляются на `/start`.
- `/legal/privacy`, `/legal/personal-data-consent`, `/legal/cookies`: явный статус черновика, содержание с якорями, навигация между документами и возврат к форме. Сохраняется `noindex`.

Общие списки услуг, процесс работы, обложка проекта и CTA переиспользуются между страницами. Маркетинговый контент рендерится на сервере; интерактивность остаётся в навигации, FAQ и форме. Иконки — Lucide, компоненты и токены — исходный shadcn preset. Проверены ширины 320, 768 и 1440 px и визуальное отображение ключевых страниц.

## Refinement

- Адаптивность проверяется на 320, 768, 1024, 1440 и 1920 px; отдельно проверяется мобильное меню на коротком экране 667×375. Поля, варианты выбора направления и кнопки переходов имеют область нажатия минимум 44 px по высоте.
- У формы исправлен контраст подсказок и текста невалидных полей. Сообщения ошибок и рамки сохраняют семантику `destructive`; цвет текста берётся из `foreground`. Видимый фокус ссылок и контролов использует контрастный outline. Токены и конфигурация preset сохранены.
- При загрузке `/start` используется shadcn Skeleton; общая навигация остаётся доступна. Отправка имеет отдельный live status; ошибка сохраняет введённые данные и переводит фокус к сообщению. Повторная отправка, успех и очистка черновика после перезагрузки проверяются в браузере. Общая ошибка страницы фокусирует заголовок и показывает состояние повторной загрузки через Next.js `retry()`.
- Отсутствующие экраны Pulsar Cloud оформлены через shadcn Empty. Пока `casePublished: false` в `src/config/projects.ts`, кейс имеет `noindex` и исключён из sitemap. После подготовки фактического материала нужно обновить контент, статус и этот флаг.
- SEO helper явно передаёт общую обложку в metadata каждой страницы: дочерние OpenGraph-объекты заменяют родительские при объединении. Проверяются canonical без query, уникальные title, description, OG/Twitter, PNG-обложка 1200×630, sitemap, `noindex` черновиков и настоящие HTTP 404.

`@axe-core/playwright` добавлен только в devDependencies. Проверка WCAG A/AA выполняется для 16 страниц на мобильном и широком экранах, а также для открытых меню, формы с ошибками, успешной отправки и 404. Исключены только невидимые `data-base-ui-focus-guard`: они перенаправляют фокус и дают ложное срабатывание `aria-hidden-focus`. Правило остаётся включённым для остального DOM; реальное удержание и возврат фокуса проверяются клавиатурой. Автоматические проверки не заменяют отдельную проверку со скринридером на целевых устройствах.

## Database / Prisma migrations

Используются Prisma **7.10.0**, SQLite и `@prisma/adapter-better-sqlite3`. `prisma/schema.prisma` описывает заявки, согласие, состояние уведомления и сохраняемый rate limit. Начальная SQL-миграция находится в `prisma/migrations`; generated client создаётся в `src/generated/prisma`.

Первый запуск и применение уже существующих миграций:

```powershell
pnpm db:validate
pnpm db:deploy
pnpm db:status
```

База по умолчанию: `prisma/pulsarweb.db`. `DATABASE_URL` имеет вид `file:./prisma/pulsarweb.db`, `file:D:/data/pulsarweb.db` на Windows или `file:/var/lib/pulsarweb/pulsarweb.db` на Linux. Относительный путь разрешается от рабочего каталога, поэтому команды запускаются из корня проекта. Пробелы и кириллица допустимы; URI encoding, query, fragment и in-memory URL не поддерживаются. Для другого расположения заранее создайте родительский каталог и предоставьте процессу приложения право записи.

Prisma CLI загружает `.env*` через тот же `@next/env`, что и Next.js. По умолчанию CLI использует development; для production задайте `NODE_ENV=production`. Переменные процесса имеют приоритет над файлами. Например, на PowerShell:

```powershell
$env:NODE_ENV = "production"
$env:DATABASE_URL = "file:D:/data/pulsarweb/pulsarweb.db"
pnpm db:deploy
pnpm db:status
pnpm start
```

Для изменения схемы в development: отредактируйте `prisma/schema.prisma`, выполните `pnpm db:migrate --name change_name`, затем `pnpm db:generate`. Сохраняйте схему и SQL-миграции в Git вместе; уже применённые миграции не переписывайте. `db:generate` не меняет данные. В production применяется только `db:deploy`; он не заменяет проверку drift. Build и запуск сервера не выполняют миграции автоматически.

**DB abstraction:** `src/lib/db/create-client.ts` создаёт адаптер с ISO 8601 timestamps и ожиданием блокировки до 5 секунд. `src/lib/db/client.ts` предоставляет ленивый серверный singleton, сохраняемый при hot reload. Прикладной код зависит от интерфейсов `LeadRepository` и `RateLimiter`; Prisma и SQL остаются в инфраструктурных реализациях. Composition root `src/modules/leads/server.ts` связывает зависимости. Для перехода на PostgreSQL меняются datasource, миграции и инфраструктурные адаптеры; domain/application не зависят от SQLite. В `app`, компонентах и бизнес-логике прямых Prisma-запросов нет.

SQLite рассчитан на Node.js-сервер с постоянным локальным диском и небольшим потоком записей. Файл БД и его journal/WAL не должны попадать в Git или bundle. Для нескольких независимых серверов или ephemeral/serverless-хранилища потребуется другая БД. Резервную копию делайте через SQLite backup API либо копируйте файл после остановки всех процессов, которые его используют.

В `prisma.config.ts` для CLI установлен `RUST_LOG=info`: в текущем окружении с `RUST_LOG=warn` Prisma 7.10.0 не создавал новую SQLite-базу. Воспроизведён [известный сбой schema engine](https://github.com/prisma/prisma/issues/29355); этот обход не включает Prisma query logging в приложении.

## Lead module

Единая форма находится на `/start`. Ссылка `/start?service=telegram` сразу открывает описание задачи. Неизвестный или повторяющийся параметр возвращает к выбору. Поддерживаются `landing-pages`, `corporate-websites`, `ecommerce`, `telegram`, `support`, `other`. Старые query `websites` → `landing-pages`, `web-systems` / `desktop` → `other`. POST сохраняет старые значения без преобразования, чтобы не менять payload hash и не ломать повторную отправку ранее сохранённых заявок. Инфраструктура — часть разработки нового проекта под ключ, а сопровождение — отдельная платная опция прежде всего для проектов PulsarWeb.

`src/modules/leads/domain` содержит общую Zod-схему, конфигурацию сценариев и порты; `ui/project-request-wizard.tsx` — один engine; `application/create-lead.ts` — use case; `infrastructure` — repository, HTTP adapter и SQLite rate limiter. Клиент и сервер используют одну схему, Route Handler не обращается к Prisma. ESLint проверяет границы слоёв.

Четыре шага: тип → задача → бюджет и срок → контакты и review. Состояние хранится в React и сохраняется при переходах назад, validation/network errors. Перезагрузка очищает черновик. Бюджет и срок необязательны. Для сопровождения вместо контекста компании можно указать название или номер проекта PulsarWeb.

`POST /api/leads` принимает `service`, `description` (20–5000), `name` (2–100), `consent: true`, `submissionId` (UUID); хотя бы один `telegram` / `phone` / `email`. Необязательны `company` (150), `companyContext` (3000), `projectReference` (150), `budget` / `timeline` из общей конфигурации, `sourceUrl`, `referrer`, `utmSource`, `utmMedium`, `utmCampaign`; honeypot `website` должен быть пустым. Строки очищаются от пробелов, Telegram приводится к `@username`, телефон — без пробелов, скобок и дефисов. Статус и вид заявки определяет сервер.

| HTTP            | Результат                                                                       |
| --------------- | ------------------------------------------------------------------------------- |
| 201             | Новая заявка: `{ "ok": true, "leadId": "…", "publicId": "PW-1001" }`            |
| 200             | Повтор с тем же `submissionId`, без новой записи и уведомления                  |
| 409             | Тот же `submissionId` с другими данными                                         |
| 422             | Ошибки полей в `error.fieldErrors`                                              |
| 400 / 413 / 415 | Неверный JSON или honeypot / тело больше 32 KiB / неподдерживаемый Content-Type |
| 403 / 429 / 503 | Чужой Origin / лимит / ошибка сохранения или конфигурации                       |

Публичный номер выдаёт атомарный счётчик `LeadSequence` внутри транзакции создания заявки; `Lead.publicId` имеет уникальный индекс. Миграция `20261015000100_project_requests` сохраняет прежние заявки, внутренние ID, контакты, согласия и статусы доставки и присваивает им публичные номера. Поле `description` в Prisma отображается на прежнюю SQL-колонку `message`. Перед применением к существующей базе сделайте SQLite backup. Начальный статус — `NEW`; доменный список содержит `NEW / CONTACTED / QUALIFIED / ESTIMATING / PROPOSAL / WON / LOST / SPAM`. Панели управления нет.

Данные фиксируются в SQLite **до** уведомлений. Ошибка Telegram не отменяет заявку. Успех показывает публичный номер, ссылку на главную и Telegram владельца. UUID пользователю не показывается. Согласие не отмечается заранее; ссылка на условия открывается отдельно.

Ответы содержат `Cache-Control: no-store` и `X-Request-Id`; ошибки — безопасные `requestId`, `error.code`, `error.message`. Контакты и описание не попадают в логи. События: `lead.created`, `lead.telegram_notification.sent`, `lead.telegram_notification.failed`. При потерянном ответе неизменённый черновик повторяет тот же UUID; при изменении данных UUID обновляется. Повторный submit блокируется и в UI, и серверной идемпотентностью.

Rate limit хранится в SQLite: 5 попыток за 10 минут на идентификатор и общий лимит 200. При `TRUST_PROXY=false` используется общий anonymous-идентификатор. Включайте `TRUST_PROXY=true` только за собственным reverse proxy, который перезаписывает `x-real-ip`, при недоступности приложения в обход proxy. Для 429 возвращается `Retry-After`.

## Optional integrations

`LeadNotification` — интерфейс уведомления из domain; `CreateLead` работает только с ним. `TelegramLeadNotification` вызывает Telegram Bot API, `LeadEmailNotification` формирует письмо через интерфейс `EmailProvider`, а `ResendEmailProvider` реализует отправку через Resend HTTP API. Composition root подключает адаптеры через `createConfiguredNotifications`; ключи и сетевые запросы остаются на сервере. Для замены email-провайдера достаточно другой реализации `EmailProvider`.

Настройки задаются в `.env.local` для разработки или окружении сервера для production:

| Канал    | Необходимые переменные                                    |
| -------- | --------------------------------------------------------- |
| Telegram | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OWNER_CHAT_ID`            |
| Resend   | `RESEND_API_KEY`, `EMAIL_FROM`, `LEAD_NOTIFICATION_EMAIL` |

Оба канала необязательны и независимы. Пустая группа отключает канал без предупреждения. Неполная группа или неверный формат отключают только этот канал и записывают `notification.configuration_invalid` с названиями проблемных переменных. Предупреждение появляется при создании обработчика заявок, без значений переменных. Страницы, health check и сохранение заявок продолжают работать; обязательные настройки `SITE_URL`, `DATABASE_URL` и `TRUST_PROXY` по-прежнему строго валидируются. После изменения конфигурации перезапустите сервер.

Для Telegram добавьте `TELEGRAM_BOT_TOKEN` в `.env.local` или окружение production. Получатель: `TELEGRAM_OWNER_CHAT_ID=885112484`; публичный контакт: `TELEGRAM_OWNER_USERNAME=galeev66`. Владелец должен предварительно открыть бота и нажать Start. После настройки перезапустите сервер. Старый `TELEGRAM_CHAT_ID` поддерживается, если `TELEGRAM_OWNER_CHAT_ID` отсутствует. Без токена канал отключён, заявки сохраняются. Реальные токены не включайте в Git. Уведомление передаётся обычным текстом без `parse_mode`, предпросмотр ссылок отключён. Длинный текст сокращается до лимита одного сообщения; полная заявка остаётся в БД. Контракт ответа проверяет наличие успешного результата и `message_id`. [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).

Для Resend укажите API key формата `re_…`, подтверждённый адрес отправителя в `EMAIL_FROM` и адрес владельца в `LEAD_NOTIFICATION_EMAIL`. В этой версии `EMAIL_FROM` принимает только email без отображаемого имени. Письмо отправляется исключительно владельцу: email посетителя используется только в `reply_to`. Формат plain text сохраняет пользовательские HTML/Markdown как текст. Если у заявки нет email, `reply_to` отсутствует. [Resend Send Email](https://resend.com/docs/api-reference/emails/send-email).

Уведомления запускаются параллельно после сохранения. Для каждого канала установлен общий deadline 8 секунд, включая чтение ответа и задержку перед повтором. Resend допускает один повтор при сетевом сбое, HTTP 5xx или 429, с неизменными телом и ключом `lead-created/<id>`. Задержка — 300 мс либо `Retry-After`; если сервер просит ждать больше секунды, попытка завершается ошибкой, чтобы не задерживать форму. Постоянные ошибки и неверные успешные ответы не повторяются. Resend хранит ключи идемпотентности 24 часа. [Документация ключей](https://resend.com/docs/dashboard/emails/idempotency-keys).

Telegram автоматически не повторяется: после потери ответа нельзя однозначно установить, было ли сообщение принято. Редиректы обоих провайдеров запрещены. Безопасная диагностика содержит provider, lead/request ID, категорию ошибки (`http`, `network`, `timeout`, `invalid-response`) и HTTP status, когда он известен; тела ответов и секреты не логируются.

В `Lead.notificationStatus` сохраняется итог: `skipped` — активных каналов нет, `sent` — все активные провайдеры приняли запрос, `partial` — принята часть, `failed` — ни один не принял. `sent` не означает доставку письма в inbox или прочтение сообщения. После сбоя процесса до записи итога возможен `pending`. Фоновой очереди и автоматической повторной обработки сохранённых заявок сейчас нет; повтор HTTP-заявки с тем же UUID не отправляет уведомления заново.

## Checks and testing

```powershell
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm format:check
```

Vitest запускает unit/integration тесты из `src`, с отдельными временными SQLite-базами и подменённой сетью для уведомлений. DB-тесты применяют всю цепочку миграций настоящим Prisma CLI к новой БД, проверяют отсутствие drift, повторный deploy без потери данных, переподключение, rollback, уникальность заявок и конкурентный rate limit. Проверяется также выбор `.env.local` / `.env.production.local`. Рабочая БД не используется.

Браузерные тесты:

```powershell
pnpm exec playwright install chromium
pnpm test:e2e
```

Если на Windows уже установлен Edge, вместо загрузки Chromium можно задать `$env:PLAYWRIGHT_CHANNEL = "msedge"`. `test:e2e` генерирует Prisma Client, собирает production-версию, создаёт временную SQLite-базу, применяет миграции и запускает отдельный сервер на `127.0.0.1:3100`; этот порт должен быть свободен. Build и сервер получают одинаковый `SITE_URL=http://127.0.0.1:3100`, чтобы статические и динамические metadata соответствовали друг другу. Telegram и email принудительно отключены и при сборке, и при запуске. После тестов сервер останавливается, временная БД удаляется. Проверяются реальные записи в БД, потерянный ответ и идемпотентный повтор, ошибки и pending-состояние, мобильная форма и навигация. Трассировки ошибок находятся в `test-results/`.

E2E использует обычный каталог `.next`. После проверки перед `pnpm start` или deployment снова выполните `pnpm build` с нужным `SITE_URL`: тестовая сборка содержит адрес порта 3100. Не запускайте несколько E2E-процессов или production build одновременно в одном checkout.

`pnpm test:e2e --partial-integrations` выполняет те же сценарии с намеренно неполными фиктивными настройками обоих каналов: сайт и заявки должны работать, каналы — отключиться с предупреждениями. Vitest проверяет адаптеры с подменённым `fetch`: payload, валидацию ответов, deadline, безопасные ошибки, правила повторов и независимость каналов. Настоящие сообщения в этих проверках не отправляются; доставку в конкретный Telegram-чат и почтовый ящик нужно проверять отдельно после настройки учётных данных.

Проверка системы заявок на 15.10.2026: `pnpm lint`, `pnpm typecheck`, `pnpm test` (127 тестов), `pnpm test:e2e` (26 сценариев, Edge) и `pnpm build` прошли. Проверены миграция прежних записей, уникальная нумерация, wizard нового проекта и сопровождения, повтор после потерянного ответа, сбои уведомлений и доступность. Реальная доставка Telegram требует токена бота и отдельно не проверялась.

## Production build

```powershell
pnpm build
pnpm start
```

Перед реальным deployment нужны корректный `SITE_URL`, постоянное хранилище SQLite, `pnpm db:deploy`, подтверждённые реквизиты и утверждённые юридические документы. Подключённые каналы уведомлений проверяются с реальными учётными данными отдельно. Сборка не выполняет миграции автоматически и не включает локальную БД в bundle.

## Project structure

- `src/app` — App Router, страницы и API.
- `src/components/ui` — компоненты заданного shadcn preset.
- `src/components/layout`, `shared` — общие компоненты сайта.
- `src/config` — данные сайта, навигация и контент.
- `src/modules/leads` — domain/application/infrastructure и UI единого wizard.
- `src/integrations` — адаптеры внешних сервисов.
- `src/lib` — env, БД, логирование, SEO.
- `prisma` — схема и воспроизводимые миграции.

## Architecture principles

Modular monolith, Server Components по умолчанию, единая схема валидации и отделённая от Next.js application-логика. Prisma используется внутри инфраструктурного слоя. Маркетинговые страницы используют общие компоненты и данные из `src/config`; unit, integration и браузерные сценарии проверяют существенные границы и пользовательские потоки.
